KEYPORT
Automatic key storage & retrieval

Design basis confirmed by the user: Rentvine; approximately 1,000 mostly single keys; staff-operated office use.

Open the interactive Anatomy demonstration

Delivered: a working offline interaction prototype, a 250-position solid CAD layout, and an integration/mechanism specification. This is a concept design. No physical cabinet has been built, no motor controller is connected, and no production key system has been deployed.

The operating concept

Staff sign in, search an address, choose the exact unit and key purpose, and use the indicated loading drawer. The machine moves standardized captive trays; staff handle only the tagged keys. Each tray has a reserved, known slot. The robot never has to grasp a loose key.

Every key or key set has a permanent, tamper-evident identification tag. The slot and tray IDs are separate from the key ID. A typed address is a request, not proof that the physical key belongs to that address. Commissioning requires a person to verify the actual key against the property before binding the tag.

The starting identification approach is a passive RFID tag with a printed machine-readable backup, attached on a nonmetal fob. A shielded read station and presence/weight sensing check one deposited set. Antenna layout, random tag orientation, metal interference, and multiple-key detection remain prototype work. A failed or ambiguous read requires correction; the cabinet must not guess.

How the mechanism works

A vertical mast travels on horizontal guide rails. A lift carriage on the mast carries a tray bed and a depth-axis extractor. The extractor engages a standardized tray-front coupling, draws the tray onto the bed, and releases it into the destination guides. Loose keys stay in the open tray through all movement.

Movement is ordered: align with the slot → pull completely clear → raise/lower to the loading transfer level while still in the rack aisle → move sideways into the loading bay → insert. On the return trip the carrier leaves the loading bay before changing to the storage height. This route avoids the dock pedestal and side guides.

The concept reserves space for an extractor actuator but does not detail its coupling linkage, motor gearing, bearings, retention latch, cable chain, or limit-switch mounts. The body model is a cutaway: exterior skins, locked service door, anti-fishing tunnel, full guard geometry and detailed fasteners must be engineered before manufacture.

Rentvine and the key database

Rentvine’s official API provides property and unit lookup using account-specific endpoints. Authentication uses an access key and secret with role-based access. A server-side adapter can read the directory; API secrets must stay off the kiosk. The existing connector’s read-only property search was successfully exercised during this design. Source: Rentvine API documentation.

Use Rentvine IDs as stable references. Do not use address text as a primary key, and do not infer a unit from a partial address. Store the account, property ID and unit ID with each key relationship. Address updates refresh the display label without changing physical key identity.

Proposed sync: periodically read property/unit changes, plus a scheduled complete reconciliation. This proposal does not depend on unverified webhook availability. A deactivated property is flagged for staff review and blocks ordinary new checkouts; its physical key record is retained until staff handle the key. Shared/master keys may map to several authorized units, but remain one physical key identity. Separate duplicate entry keys get separate key IDs.

The key service owns custody and inventory. Rentvine remains the source of property/unit identity. Returning a key does not modify a lease, payment, work order, or property record. Staff access rights and any future write-back require a separate implementation.

Original ClassCAD verification and browser checks

  • Native model: 338 solids, including 250 individual hollow trays; external bounds 1,400 × 650 × 1,900 mm.
  • Tray volume: 99,468 mm³, matching 90 × 150 × 45 minus the 84 × 144 × 42 cavity.
  • Final STEP file reimport: all 338 solids, same dimensions, and total solid volume 164,688,833 mm³. The exporter reported a warning/error level despite writing the file; successful reimport supplies the useful validation. An independent external CAD application has not been tested.
  • 21,000 sampled carrier-envelope positions on withdrawal, height adjustment, lateral transfer and docking routes showed zero intersections with modeled fixed boxes. No stored tray envelopes overlap. This excludes the moving gripper linkage, cables, safety enclosure and manufacturing tolerances.
  • Browser acceptance: retrieval presentation, pickup and custody update, empty-tray return, wrong-key rejection, verified return, unit search and no-match blocking passed. Reduced-motion controls, desktop and phone layouts, and both themes were checked. Normal-speed motion reached the loading drawer.

These checks validate the digital concept within the stated scope. They do not establish physical reliability, retrieval time, electrical safety, load capacity, accessibility compliance, or resistance to forced access.

Path to a working cabinet

  1. Build one 24-position mechanical pilot. Use representative real keys, tags, rings and fobs. Set the load envelope and test the tray coupling and RFID read station before scaling.
  2. Implement the durable key service and controller protocol. Add staff authentication, property/unit sync, slot reservation, custody events, idempotent requests and recovery reconciliation. The delivered HTML is a UI/state demonstration, not this production service.
  3. Test failure paths with hardware. Include wrong tags, unreadable tags, double deposits, keys protruding above the tray, occupied targets, missed pickups, hand-in-drawer detection, motor stalls, network loss, and power removal during every transaction phase.
  4. Agree measurable acceptance gates. Suggested pilot target: at least 10,000 mixed store/retrieve cycles with zero wrong-key releases or unexplained inventory changes; log all recoverable jams, read failures and intervention rates. This is a proposed test target, not an achieved result or a safety certification.
  5. Scale to one 250-position module, then four. Confirm service access, anchoring, queue behavior, maintenance procedure and spare parts. Commission every key using a physical verification process.

No component quotations or fabrication costs were collected. The next procurement step is a mechanical integrator’s review of this geometry, the transfer coupling, tag testing, guarding and controller requirements.
